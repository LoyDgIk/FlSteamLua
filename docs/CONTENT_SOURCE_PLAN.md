# 内容源与新入库框架实施计划

状态：核心模块与界面已实施，正在集中验证。阶段表是验收标准，不是测试通过记录。

依据：2026-11-01 提交的《内容源架构 v1》，以及当前 Dart 服务与入库调用路径。

## 一、最终用户模型

统一入口为“内容源”。订阅、JS 脚本、本地内容是来源类型；Lua、清单 ID、清单文件是来源能力。页面使用统一列表和能力筛选，不再以“订阅清单 / JS 清单源”作为顶层 Tab，各类型继续使用适合自身的配置表单。

库页面保持两个 Tab：默认“Lua 库”，第二个“Steam 游戏库”。这两个 Tab 与来源类型无关。

一次入库选择一个必需的 Lua 来源，以及一个可选的清单来源。反馈分别报告 Lua 写入、版本固定、清单文件写入；不能用“入库成功”暗示游戏下载一定成功。

## 二、现有代码的复用与缺口

| 当前代码 | 复用内容 | 必要改动 |
| --- | --- | --- |
| `lib/features/manifests/manifest_script_parser.dart` | 元数据与参数解析 | 增加能力声明解析 |
| `lib/features/manifests/manifest_models.dart` | 脚本定义、配置与下载产物 | 增加声明与结构化结果信息 |
| `lib/features/manifests/manifest_source_service.dart` | QuickJS、HTTP、秘密字段、测试与下载 | 由脚本适配器调用，补齐独立 manifest pins 结果 |
| `lib/features/key_cache/key_cache_service.dart` | 订阅、更新、加密缓存、元数据与 Lua 生成 | 按指定订阅读取与生成，不能通过切换全局当前源实现 |
| `lib/features/library/library_service.dart` | Lua 目录、备份、写入和扫描 | 提供已解析 Lua 的窄写入接口，供统一提交协调 |
| `lib/features/steam_protocol/manifest/depot_manifest.dart` | 实际 manifest 容器解析 | 复用结构、大小、内部 depot/GID 校验 |
| `lib/features/tools/manifest_monitor.dart` | 读取日志、补充请求清单 | 保留机制并纠正界面命名 |
| `lib/core/task_center.dart` | 进度、取消、跨页任务与失败 | 准备和提交纳入一个入库任务 |

当前 `LibraryService.importFiles` 逐文件写入、收集错误，不能保证整次计划全部成功。新框架不能仅在这个方法前增加来源选择框。

脚本结果现支持多文件与结构化 manifest pins。订阅缓存读取、元数据刷新和 Lua 生成均显式传入 sourceId；不存在全局激活订阅。

## 三、模块划分

新代码集中于 `lib/features/content_sources/`：

- `content_models.dart`：定义、状态、能力、请求、计划、产物、内容包和导入结果。
- `content_source_registry.dart`：统一列出与筛选来源，分派测试、更新和获取。
- `adapters/script_content_source.dart`：复用现有脚本服务。
- `adapters/subscription_content_source.dart`：复用现有订阅服务。
- `content_resolver.dart`：获取、解包、验证和合并，产出最终内容包，不修改 Steam 目录。
- `content_import_service.dart`：目标预览、覆盖策略、备份、提交、回滚和库刷新。
- `content_sources_page.dart`、`content_import_dialog.dart`：统一管理页与入库计划界面。

本地拖拽作为一次性的本地来源进入相同解析流程，不把每次拖入的文件永久注册成一张来源卡片。清单请求监听独立存在，不注册成内容源。

原服务继续保存自己的配置和秘密字段。注册表只增加统一启用状态，不复制两套配置，也不保存全局选中的来源。项目尚未发布，不增加旧配置迁移或历史激活状态兼容。

## 四、领域模型补充

沿用 v1 的类型，并补齐实际调用所需的信息：

| 模型 | 补充 | 用途 |
| --- | --- | --- |
| 来源状态 | 配置状态、最后更新、最近测试结果 | 与来源能力声明分离 |
| 获取请求 | AppID、本次请求的能力集合、DLC/版本固定选项 | 明确多能力来源此次承担的职责 |
| 产物 | `sourceId`，清单文件对应的 depot/GID | 冲突和导入结果可追溯 |
| 内容包 | 目标 AppID、实际解析产物 | 不用文件名推断目标游戏 |
| 导入结果 | 已写入、跳过、备份、失败项目 | 全部跳过不能显示成功写入 |

统一 ID 使用 `script:<ID>`、`subscription:<ID>`，避免跨类型 ID 冲突。用户自定义来源名称不随界面语言变换。

manifest ID 全程保存为十进制字符串，范围校验使用 `BigInt`，不经 JS Number 或浮点数转换。

## 五、能力声明与请求契约

能力声明表示来源可以提供什么，本次请求表示入库需要什么。二者必须分开：

- 选作 Lua 来源，必须声明 `lua` 且实际返回有效 Lua。
- 明确选作清单来源，必须有清单能力且实际返回所请求的清单产物。
- 用户不指定清单来源，缺少清单不导致入库失败。
- 同一来源兼任两种职责，只获取一次，验证两种所需产物。
- 多能力来源只被请求提供 Lua 时，不因缺少未请求的清单而失败。
- 返回超出声明的内容不自动升级能力，也不自动扩大写入范围；可识别的不相关文件不写入 Steam。

JS 保留 v1 的 `@provides`、`@manifest-types`。未知能力、冲突或不完整声明在脚本导入时明确报错。未声明能力的脚本按 `manifestFiles` 解释；实际若只返回 Lua，应提示补充声明，不能偷偷升级成 Lua 来源。

- `@manifest-types codes` 表示来源可按 `{depotId, manifestId, requestCode}` 返回内核清单请求码。内核本地代理只调用显式选择且声明该能力的内容源，不另建一套清单脚本或全局当前源。
- 针对“只提供 ID”的脚本，需要扩展返回协议，例如在结果对象中提供 `manifestPins: [{depotId, manifestId}]`。仅解析 Lua 中的 `setManifestid` 不足以支持独立清单 ID 来源。原文件返回协议继续支持。

订阅初始仅声明 `lua`。其 Lua 内已有 `setManifestid` 可以被解析并参与冲突检测，但不代表该订阅已具备独立的清单 ID 查询能力。

内置脚本必须逐个以实际结果样本验证后标注。当前 LuaTools 返回 ZIP；Ryuu、Hubcap 有 Lua/ZIP 分支；ManifestHub2 有单个 manifest/打包分支。这些源码分支只能说明候选格式，不能证明远端包的实际完整性。

## 六、解析、合并与写入

1. 固定本次 AppID、来源配置和计划，只读取本次指定的来源。
2. 获取产物至应用暂存目录，检查取消；在线准备订阅元数据与离线生成明确区分。
3. 在外部输入边界完成解包、路径、体积、格式与声明校验。
4. Lua 只做文本与已知配置语法检查，不执行 Lua。提取其中已有 pins；核对主 AppID，避免将其他游戏的配置写入当前目标。
5. 合并独立来源的 pins：相同 depot/GID 去重，不同 GID 报告来源冲突，不静默覆盖。
6. 清单文件复用 `DepotManifest.parse` 检查结构和内部 depot/GID，与文件命名及所选 pins 交叉核对。不能只看扩展名或前四字节。
7. 将选中的 manifest pins 真正应用到最终 Lua 的 `setManifestid`，预览变更。已有相同项保持，不同项按冲突规则处理，不能只把 pins 放进一个未使用的列表。
8. 所有必需产物验证成功后，预览 Lua 路径、depotcache 路径、覆盖和备份清单。
9. 提交前在各目标目录暂存文件并保存被替换文件的备份，依次提交；任一失败恢复本次已改动的文件，再报告结果。
10. 成功后只扫描一次库，更新游戏名称、封面和导入记录。

多个目标文件之间不能声称有单次文件系统原子性；这里承诺的是提交协调和失败回滚。回滚失败必须显示具体文件及备份位置，不能继续显示成功。取消发生在准备阶段时不写入目标目录；提交开始后完成提交或回滚再结束任务。

Lua 与 depotcache 覆盖由同一次预览决定，不能分别弹出多轮重复确认。只含清单的包可以用于独立“补充清单”，但不能作为新增 Lua 游戏入库成功。

## 七、页面与入口接线

内容源页使用统一卡片，筛选“全部 / Lua / 清单 / 已启用 / 异常”。卡片区分类型、能力、配置状态、更新时间和测试结果；操作按实际类型提供编辑、测试、更新、启停和删除。没有对应操作的类型不显示虚假按钮。

添加菜单提供订阅配置、JS 导入、本地导入。来源表单继续复用订阅与 JS 的字段，不强行拼成同一张表单。

入库对话框只包含 Lua 来源必选项、可选清单来源、适用的 DLC/版本选项、产物预览与一次提交。默认清单选择可以跟随双能力 Lua 来源，但用户仍能改成其他来源或不指定。

这些调用统一接入新流程：商店添加、游戏详情下载、Lua 库导入与拖拽、订阅生成后的入库。编辑现有 Lua、独立补充清单保持各自语义，不强制重新选择 Lua 来源。

所有来源管理入口直接打开内容源页；删除原订阅页与脚本页，不保留兼容包装。底层脚本执行服务继续承担其原有职责。

全部新文案使用 ARB 和生成式 `AppLocalizations`。数量、AppID、来源名及错误细节作为参数，页面不再新增中英双字符串 helper。卡片、菜单、弹窗复用已引入的 FlClash 组件。

## 八、清单请求监听的边界

沿用 `ManifestMonitor`，第一阶段不为了改名再增加一个转发型 `ManifestRecoveryService`。需要进一步协调批次时再扩展其职责。

界面命名为“清单请求监听”或“清单补充”：读取 Steam 后续 manifest 请求，从备用渠道下载并写入 depotcache。默认从日志末尾监听，停止监听不等于取消已经提交的文件写入。

不标注“下载失败自动修复”：现有实现不识别 Steam 下载失败、不重启 Steam，也不重新触发游戏下载。入库完成后可以提供“开启清单请求监听”的独立操作，不默认开启。

## 九、实施顺序与阶段验收

| 阶段 | 交付 | 验收条件 |
| --- | --- | --- |
| 1. 契约 | 模型、稳定 ID、能力解析、显式来源缓存 | 来源隔离、能力默认值与错误声明有测试 |
| 2. 获取与解析 | 两种适配器、按指定订阅生成、Resolver | 仅 Lua、组合来源、单源双能力、缺产物、pins 冲突均有实际夹具 |
| 3. 提交闭环 | 预览、Lua pins 合并、manifest 写入、回滚 | 多目标第二次写入失败时恢复第一次写入；取消不留半套结果 |
| 4. 统一界面 | 内容源页、入库对话框、所有入口接线 | 能力筛选有效，旧入口重定向，拖拽仍可用，FlClash 交互与 ARB 文案接入 |
| 5. 最终验证 | 原生分析、测试、Windows 构建及界面验收 | 测试和构建以同一最终代码执行，真实联网验证与隔离夹具结果分别记录 |

第一条纵向交付先打通“选指定订阅 → 准备元数据 → 生成 Lua → 预览 → 入库 → Lua 库可见”，随后加入脚本和独立清单组合，最后切换所有入口。阶段间保留原可用流程，完成接线后删除旧的分叉选择逻辑。

## 十、测试清单

- 解析三种清单能力组合、旧脚本默认值、非法/冲突声明和无 Lua 声明禁选。
- 同名跨类型 ID、DPAPI 秘密字段、来源启停与缓存隔离。
- 按指定订阅读取与生成，不存在全局当前源；未缓存元数据的在线准备和离线错误分别验证。
- 仅 Lua 成功；声明 Lua 却缺产物失败；明确选择清单却无产物失败。
- 两来源组合、单源只调用一次、用户取消默认清单、不重复下载。
- Lua 现有 pins 与独立 pins 合并、重复去重、冲突失败，最终 Lua 包含实际固定版本配置。
- 路径穿越、链接、超限压缩内容、伪造 manifest、文件名与内部 depot/GID 不符，不产生目标写入。
- 覆盖、全部跳过、提交失败、回滚失败、准备时取消以及成功后单次扫描。
- 能力筛选、统一内容源列表、旧入口重定向、拖拽入库、无匹配来源时可配置来源。
- 清单监听只处理请求补充，不被显示成失败自动修复。

测试以现有 `flutter analyze`、串行 `flutter test` 和 `flutter build windows --release` 为项目入口；涉及 QuickJS 的测试仍加载 Windows 插件。文档规划不计为这些检查通过。
